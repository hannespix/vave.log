# Connected project workflows

The user wants to move between related work without selecting the same project repeatedly, see whether project hours and deadlines remain plausible, and keep the interface uncluttered. The user has explicitly delegated design, implementation, main integration and deployment decisions. This extends the existing application; no new infrastructure or dependencies.

## Experience

- A workspace-scoped navigation state owns the selected project and view. Project task counts open Tasks with that project selected. Project names in task/time/report/finance views lead back to the matching project. Project links to time, reports, planning and invoices apply their project filters. Browser history and reload preserve safe view context using a hash; auth callback query parameters remain untouched. Invalid, unavailable or cross-workspace IDs never broaden a requested project silently.
- Tasks has search, a project selector and quick choices All / Mine / Overdue. Assignee, status and due-date filters live in a collapsible filter section. Active filters are visible and individually removable; reset is one action. Empty results explain the filter and offer reset. Dates use workspace timezone. Editing and creating keep project context, and switching views does not retain hidden contradictory filters.
- Project cards keep current period hours and explicit scope. Tasks and time are direct links; an unobtrusive analysis action opens a dialog. Editing and new task/time actions remain in dialogs. No recurring demo banners are added.
- Project analysis is manager/owner-only and loads on demand, independently of the period filter. It uses all recorded project time through today, excluding future entries, from one database snapshot. It shows budget used/remaining, reported progress, forecast total/remaining effort, recent team pace and deadline outcome. Explanations and calculation assumptions are disclosed progressively. Members retain project/task navigation without receiving team aggregates or finance data.

## Planning and analysis contract

Projects gain optional nullable `due_date` and `progress_percent` (0–100). `progress_updated_at` is maintained by the database and is not client writable. Existing project writers can update planning; old clients omitting fields preserve them. Dates are validated at database and client boundaries. No existing business values or real progress are invented.

`project_insight(p_workspace_id,p_project_id)` is a SECURITY INVOKER read-only RPC with explicit authenticated owner/manager authorization, workspace/project matching and constrained search path. It returns `ProjectInsight`: `{project, as_of, progress_date, total_minutes, first_work_date, last_work_date, recent_daily:[{work_date,minutes}], tasks:{total,done,overdue}}`. All totals are team-wide and include draft/submitted/approved records, exclude future dates and running timers. `recent_daily` covers the last 28 calendar days including today. `as_of` is today's date in the workspace timezone. `progress_date` is the server-managed progress update date in that same timezone; MCP additionally returns the same pure forecast used by the GUI. Missing/unauthorized projects fail closed. No 1,000-row truncation is permitted. MCP exposes the same planning fields and insight read operation.

Forecasts require explicit reported progress greater than 0 and less than 100 and recorded effort. Projected effort = used minutes / progress fraction; remaining = projected minus used. Progress older than 14 calendar days is stale and suppresses confident forecasts. Recent pace = minutes in observation window / observed calendar days, using max(first work date, today minus 27 days); require at least 7 observed days and 3 distinct logged days. Predicted finish = today plus ceiling(remaining / calendar-day pace). This is a transparent constant-pace scenario, not a probability, staffing commitment or holiday-aware schedule. No budget means budget outcome unknown; no deadline means date outcome unknown. Zero pace, stale/missing progress, paused/archived projects or insufficient history never produce a green assurance. Task completion ratio is separate and explicitly unweighted, never silently used as physical project progress. A reported 100% is described as complete according to the reported progress, not a historical completion date.

Demo planning may be initialized only for unmodified demo seed projects with unmistakable provenance, without claiming real progress. Real projects and user-edited planning must be preserved. If safe demo initialization requires a separate user action, prefer leaving planning unset to overwriting edits.

## Verification and release

Test navigation/history parsing, stale/foreign project IDs, filter combinations and reset, project-prefilled editors, permission denials and aggregate scope. Forecast tests include zero/missing/stale progress, no budget/deadline, overdue projects, 100%, future entries, paused state, insufficient pace and dates across months. EN/DE/ZH must cover all new copy. CI browser tests cover desktop/mobile links, filters, dialog, role visibility and overflow. Apply an additive migration only after local database tests, run rollback live checks, inspect advisors, merge after CI passes and deploy the exact matching source tree preserving owner-only Site access.
