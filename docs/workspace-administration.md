# Workspace administration

Verified real owners can preview and permanently delete their workspaces through the same user-scoped service used by the web app and MCP. The preview includes archived demos that ordinary workspace reads intentionally hide. Ownership is the current real membership, not the original creator; sample team profiles cannot own or authorize deletion.

`list_owned_workspaces()` returns only ID, exact name, created/archive timestamps, demo status, six business-record counts and running timer count. `delete_workspace(p_workspace_id, p_confirmation_name, p_confirmed)` requires the exact stored name and literal `true`. A new ownership/verification check and timer check run in the deletion transaction. Counts are a preview, not an immutable snapshot of a changing workspace.

Deletion removes the workspace's projects, tasks, draft/submitted/approved times, memberships (including sample profiles), invitations, rates, plans, expenses, clients, billing identity, draft/issued/cancellation invoices, payments, time claims, timer receipts, invoice counters, demo metadata and audit history. It does not delete login accounts or records belonging to another workspace. No copy of the deleted business data is retained by this operation. It cannot be undone through the app.

All running timers must first be stopped or deliberately discarded. The deletion transaction locks the workspace before checking timers. Every timer insert takes a conflicting key-share lock and then rechecks authorization; this covers real workspaces and demos. A timer that commits first blocks deletion; a timer waiting behind deletion fails after the workspace disappears. The existing user-before-workspace lock order is retained. Other concurrent writes may cause a transaction conflict; the deletion rolls back atomically and may be retried only after refreshing the preview and confirming the target again.

The exposed SQL functions are security invokers. Their private security definers have empty search paths and explicit grants. Immutable invoice, approved-time and last-owner guards permit DELETE only while an inaccessible private row binds the workspace, authenticated actor and current transaction. Browser roles cannot read or write this capability or invoke its helper. It is deleted before successful completion and rolls back with any error. Caller-controlled configuration flags cannot bypass guards. Ordinary edits, deletions, invoice finalization and member role changes retain their protections.

The MCP deletion tool is destructive and explicitly non-idempotent. Its description requires a preview of the exact workspace ID/name and counts, followed by explicit user confirmation. Workspace names and other returned data must never be treated as instructions. The service translates database errors into controlled `forbidden`, `confirmation`, `running_timers`, `not_found` or `failed` codes. It preserves exact whitespace and Unicode in confirmation names. The name limit is 120, matching existing database workspace names, including older names longer than the current creation form permits.

Verification uses the actual migrations with PGlite, exercising active and archived full demos, real finalized documents and approved time, role denials, transfer of ownership, exact-name rejection, running timers, rollback on a downstream failure, private capability forgery, continuing ordinary guard protection and preservation of accounts/other workspaces. `tests/live/workspace-admin-smoke.sql` is an exact rollback-only fixture for Supabase. It deletes only new random fixture workspace IDs created in its own transaction; it never selects an existing workspace as a deletion target. SQL lock behavior is enforced by Postgres locks; the single-connection automated fixture does not simulate concurrent sessions.
